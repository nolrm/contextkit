# Analyze Project for ContextKit Customization

Generate the project-specific content of `.contextkit/standards/` by reading the actual codebase — most valuable on a brownfield project that has no written conventions at all. Runs once, at the start of `/ck setup`. Ongoing refinement afterward goes through `/learn` (a correction becomes a rule) and `/ck tidy` (prune what's unused) — this skill seeds the standards, it doesn't own them forever.

## What Gets Written

**Always:**

- `.contextkit/standards/index.md` — the always-loaded index (≤ 50 lines). Every session reads it, so it holds only: one line on what the project is, the must/must-not rules an agent would otherwise break, the exact commands that matter, and a "When you touch X → read Y" table pointing at the topic files below. Detail lives in topic files, not here.
- `.contextkit/config.yml` → `context_rules` — maps each topic file to the paths it applies to, so tools load it only when those files are touched (see **Context Rules** below).

**For single-package projects:** `.contextkit/standards/code-style.md`, `testing.md`, `architecture.md`, `ai-guidelines.md`, `workflows.md`, `glossary.md`, `README.md`.

**For monorepos** (ask the user — frontend, backend, or both — if a multi-package layout is detected): the same topic files under `.contextkit/standards/frontend/` and `.contextkit/standards/backend/`; shared cross-cutting standards stay at the top level.

## Step 0 — Read What's Already Known

Before scanning any code, check what's already been recorded:

- Custom content in `AGENTS.md`/`CLAUDE.md` outside the `<!-- Generated by ContextKit -->` markers — often written before ContextKit was ever installed.
- `.contextkit/corrections.md`, if it exists.
- Any `.contextkit/standards/*.md` file that already has real content, not a skeleton placeholder.

Treat this as a first-class input to fold into what you write, not just something to avoid clobbering. A brownfield project's tribal knowledge is frequently already written down somewhere — don't rediscover from scratch what a human already told the agent.

## Update Strategy

Before writing any file, check its current content:

- **Placeholder** (only "Content will be generated by running `/ck setup`" or `[YOUR_DOMAIN]` markers) → replace entirely.
- **Real content** (project-specific rules, custom sections, hand-written notes) → improve and augment only. Add new sections, update outdated references, fill gaps. **Never delete or overwrite existing custom content.**

This lets standards evolve and improve across multiple `/ck setup` runs without losing prior work.

## The Non-Inferable Filter — What Actually Earns a Line

The Scan Categories below are for *your own* understanding of the codebase — they tell you what to look at, not what to write down. Before a candidate rule goes into `code-style.md`, `architecture.md`, `ai-guidelines.md`, or `workflows.md`, it must pass all three checks:

1. **Not derivable from a manifest, config file, or directory listing a coding agent can already read.** A framework name, a dependency list, "this project uses TypeScript" — an agent gets these for free from `package.json`, `tsconfig.json`, `ls`. Writing them down taxes every future turn to restate what one `Glob`/`Read` already answers.
2. **Grounded in a specific file you actually read.** Cite it (`// see src/api/client.ts` inline, or a short parenthetical). A rule with no source is a guess, not an observation.
3. **Changes what an agent would otherwise do.** If a reasonable agent reading this codebase would naturally do the same thing anyway, the rule adds tokens without changing behavior.

**Always exclude:** directory trees, dependency/library inventories ("uses Redux, uses Jest"), generic framework best-practice advice not tied to something this codebase does differently, restating what the code's own naming/types already make obvious — **and anything an existing linter, formatter, or type-checker already enforces.** If ESLint/Prettier/`tsconfig` strict mode already auto-fixes or auto-rejects it, the tool is the enforcement; a prose rule saying the same thing only adds tokens. Only a *custom or non-default* config rule earns a line, and only if the config file itself wouldn't make it obvious to an agent that reads it.

**Always include when found:** exact commands this project actually uses (the literal `npm run test:unit -- --watch=false` from `package.json`, not "run tests"); a hard constraint an agent would otherwise violate (a global side effect, an ordering requirement, "this function is called from three places, don't rename it"); a convention that contradicts the obvious default choice (cite the file); domain terms this codebase's identifiers don't spell out on their own.

This is a hard filter, not a style preference — generated repository-context files were measured to *reduce* task success by 0.5–2% and *raise* inference cost over 20%, while human-curated files built to this same non-inferable-only standard *improved* success by ~4%. See `docs/token-efficiency.md` § Evidence.

## When Patterns Conflict

Real codebases accumulate more than one era of convention — two import styles, two error-handling approaches. Don't silently pick one and present it as *the* rule. Either note which is dominant (by recency or frequency) and name the exception, or ask the user which is canonical using your multiple-choice tool (Claude Code `AskUserQuestion`, Codex `request_user_input`). Never invent a "best practice" the codebase doesn't actually follow.

## Scope — How Much to Read

For a large repo, don't attempt exhaustive reads. Prefer recently-modified and most-imported files as representative samples per category. If coverage was partial, say so plainly in your reply (e.g. "sampled ~40 files in `src/api/`, not all 300") rather than implying a complete scan.

## Scan Categories

Build your own understanding against each of these; run the Non-Inferable Filter above on anything before it becomes file content. Most of structure/dependency scanning informs you without directly becoming written output.

1. **Structure** — framework, build tool, package manager, monorepo layout (Turborepo/Nx/Lerna/workspaces), directory organization.
2. **Dependencies** — UI/styling, state management, testing, API client, and utility libraries in use (read `package.json`/equivalent once; don't enumerate names into a standards file — see the filter above).
3. **Configuration** — linter/formatter/type-checker rules and strictness (needed for the linter-enforcement exclusion above), build config, env/secrets handling, containerization.
4. **Code patterns** — import/export style, component or module structure, naming conventions, error handling, API integration, state management.
5. **Testing & quality** — strategy, mocking conventions, file organization, unit vs. e2e balance, any quality/metrics tooling.
6. **Deployment & DevOps** — CI/CD pipeline, environment management, monitoring, security scanning.
7. **Documentation** — existing README/API-doc structure, commenting conventions, changelog/versioning practice.
8. **Glossary** — recurring domain vocabulary, entity/model names with business meaning, module/service names, shorthand or legacy aliases. Add discovered terms to `.contextkit/standards/glossary.md`; append to existing entries, never remove them.

## Output Density — Generate Compact by Default

Check `.contextkit/config.yml` → `diagrams_in_docs` (default false if missing) before writing any standards file:

- If false: no Mermaid diagrams unless asked. For a simple relationship, use an inline arrow chain (`input → transform → output`) instead.
- If true: diagrams are allowed where they're genuinely the clearest option — still not the default for something a sentence already covers.
- Prose bullets over multi-column tables where both convey the same rule. Short bullets, not paragraphs — one rule per bullet.
- One real code example (pulled from this project) beats three paragraphs of style description.
- State a rule once — no repeated rationale across sections.

This applies to newly generated files; existing oversized files are retrofit via `/ck tidy`, not by re-running `/ck setup`.

## Self-Check Before Writing

For every exact command you cite, re-verify it against the current `package.json` (or equivalent) immediately before writing it — on a long-running analysis, catch a command that went stale or was mis-copied partway through, rather than shipping a hallucinated one.

## Always-Loaded Budget

Only `index.md` (plus `AGENTS.md`/`CLAUDE.md`) loads every session; topic files load when their `context_rules` paths are touched. After writing `index.md`, count its lines. If it exceeds **50 lines**, move detail into the matching topic file and leave a row in the "read when" table instead. `ck check` warns when the always-loaded set grows past `context_budget_lines` (default 400).

## Context Rules — Load Topic Files Only Where They Apply

After writing the topic files, set `context_rules` in `.contextkit/config.yml` — one entry per topic file, with globs taken from this project's real layout:

```yaml
context_rules:
  - file: standards/testing.md
    paths: ['**/*.test.*', '**/*.spec.*', '**/__tests__/**']
  - file: standards/code-style.md
    paths: ['src/**', 'lib/**']
```

- `file` is relative to `.contextkit/`. `paths` are repo-relative globs.
- Topic files with no sensible path scope (glossary, architecture) stay out — the index's "read when" table points at them instead.
- Then run `ck update --force` (or `ck <platform>`): the CLI renders these as `.claude/rules/` (`paths:`), `.cursor/rules/*.mdc` (`globs:`), and `.github/instructions/*.instructions.md` (`applyTo:`) for each installed tool.

## Mark Generated Rules for Review

Every rule you add (new or updated) gets a trailing `<!-- ck:unreviewed -->` marker on its own line directly after it:

```markdown
- Resolve import order with `eslint-plugin-simple-import-sort`, not manual grouping (see `.eslintrc.js`).
<!-- ck:unreviewed -->
```

This is the human-review signal the evidence above rewards — a rule stops being "unreviewed" (delete the marker) only once a person has actually read and confirmed it. `ck check` reports the remaining `ck:unreviewed` count per file so stale, never-reviewed content doesn't silently accumulate. Never add the marker to content a human already wrote or already reviewed — only to what this run generates.
