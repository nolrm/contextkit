# Learn

Turn a correction into a rule so the mistake doesn't repeat.

## Usage

```
/learn "we use the MUI wrapper, never raw MUI"
/learn                 # learn from the correction just made in this conversation
```

## Steps

1. **Get the lesson.** From the argument, or from the user's most recent correction in this conversation. State it as one rule: what to do (or not do), and when it applies. If unclear, ask with 2–3 options.
2. **Check it isn't already there.** Search `.contextkit/standards/`, `.contextkit/corrections.md`, `AGENTS.md`, and `CLAUDE.md`. If an existing rule covers it, sharpen that rule instead of adding a new one.
3. **Pick the right home:**

   | The rule is about… | Write it to |
   |---|---|
   | A specific area (tests, API, components, a feature) | The matching topic file in `.contextkit/standards/` (e.g. `testing.md`) |
   | Project-wide must/must-not | `.contextkit/standards/index.md` (keep it short) |
   | A term or name | `.contextkit/standards/glossary.md` |
   | An architecture decision | `.contextkit/standards/architecture.md` (Decision, Rationale) |

   If ContextKit isn't installed (no `.contextkit/`), write to `AGENTS.md` (or `CLAUDE.md` if that's the only instructions file) outside any `<!-- Generated by ContextKit -->` block.
4. **Write it** in the file's existing style. One line, plus a short reason if it isn't obvious. Never edit inside `<!-- Generated by ContextKit -->` … `<!-- End ContextKit -->`.
5. **Log it.** Run `ck note "<rule>" --category "Rule Updates"` if the `ck` CLI is available; otherwise append a dated line to `.contextkit/corrections.md`.
6. **Reply** with one line: the rule and where it went.

## Don't

- Don't add one-off preferences that only apply to the current task.
- Don't add rules a linter or formatter already enforces.
- Don't delete existing rules — mark them `~~old rule~~ — replaced: <reason>`.
